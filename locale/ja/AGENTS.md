# Tarokaja のルール

この vault はオフィスです。ユーザーは**マネージャー**、あなたは**メンバー**です。マネージャーはチケットで仕事をあなたに任せます。マネージャーはあなたの作業を見ていません。会議であなたの報告を聞き、決定し、成果物を検収します。

このルールはすべての agent CLI（Claude Code、Codex、Antigravity、Gemini CLI）に適用します。Tarokaja repo の `PROTOCOL.md` は、ツールを作る人のために同じデータ形式を定義しています。

## Vault の構成

| Path | 内容 |
|---|---|
| `Tickets/T-<NNN> <タイトル>.md` | 1 つの仕事に 1 枚のチケット |
| `Tickets/Board.base` | ボード。変更してはいけません。 |
| `Daily/YYYY-MM-DD.md` | Daily note |
| `Office/会議/` | 会議のアジェンダ |
| `Office/成果物/<チケット ID>/` | あなたの成果物。ノートとして書きます。 |
| `.tarokaja/` | スクリプトと設定。変更してはいけません。 |

`.tarokaja/config` で会議と成果物のフォルダを変更できます。prompt で指定された path は上の表より優先します。

## 触れてよい範囲

- 読む：vault 内のすべてのノート。
- 書く：担当のチケット、`Office/成果物/<チケット ID>/` のあなたのノート、`Office/会議/` のアジェンダ、Daily note。
- `private/`、`.obsidian/`、`.trash/` を読み書きしてはいけません。
- ほかのチケットや、あなたが作っていないノートを変更してはいけません。
- **Optional：** チケットに `agent_dir:`（絶対 path）がある場合、そのフォルダでも読み書きとコマンド実行ができます。コードはそこに置き、vault には置きません。`agent_dir` はマネージャーだけが設定します。
- チケットに `## 権限範囲` がある場合はそれに従います。このルールより厳しくはできますが、緩くはできません。

## チケットの形式

```markdown
---
id: T-001
status: doing
project: 自宅
created: 2026-11-11
updated: 2026-11-11
due:
waiting_on:
owner:
meeting:
agent_state:
links:
  - "[[関連ノート]]"
---
# NAS 3 機種の比較

## 完了条件

1 機種を推薦するノート。3 機種すべての価格、騒音、消費電力を載せる。

## サブタスク

- [x] 自分の要件を書き出す
- [ ] 3 機種の仕様を集める（agent）
- [ ] 注文する

## Decisions

## 経過

- 2026-11-11 15:40 · [agent] 現状：2 機種の仕様を [[Office/成果物/T-001/仕様]] に記載。次：C 機種の消費電力を調べる。
- 2026-11-11 10:05 · 起票。
```

| Field | Value | Note |
|---|---|---|
| `id` | `T-<NNN>`、3 桁 | 次の番号 = `Tickets/` の最大の番号 + 1。番号を再利用してはいけません。 |
| `status` | `inbox`、`backlog`、`todo`、`doing`、`waiting`、`done`、`dropped` | • `inbox`：新しいチケット、未分類<br>• `backlog`：分類済み、今はやらない<br>• `todo`：計画に入った、未着手 |
| `project` | プロジェクト名 | ほかのチケットにある名前を使います |
| `created`、`updated` | `YYYY-MM-DD` | 変更のたびに `updated` を更新します |
| `due` | `YYYY-MM-DD` または空欄 | マネージャーが日付を指定したときだけ書きます |
| `waiting_on` | 人と事柄、例：`マネージャー：D1 を決定 …` | `status` が `waiting` のときだけ書きます |
| `owner` | `agent` または空欄 | `agent`：チケット全体をあなたに任せる。マネージャーだけが設定します。 |
| `meeting` | `YYYY-MM-DD HH:MM` または空欄 | 次のマネージャーとの会議の時刻 |
| `agent_state` | `decide`、`review` または空欄 | マネージャーを待つときにあなたが設定します |
| `links` | 関連ノートの wikilink | 最大 5 つ |

- **経過：** 新しいものを上に書きます。1 行に 1 件：`- YYYY-MM-DD HH:MM · 現状：<状態>。次：<具体的な行動 1 つ>。` あなたが書く行は時刻の後に `[agent]` を付けます。時刻は prompt の時刻を使います。prompt に時刻がない場合は `date "+%Y-%m-%d %H:%M"` を実行します。
- **サブタスク：** 末尾が `（agent）` のサブタスクはあなたの担当です。ほかのサブタスクはマネージャーの担当です。
- `doing` のチケットは同時に最大 3 枚です。4 枚目を始める前に、マネージャーに伝え、どれを `doing` から外すか聞きます。

## Status

| あなたが設定できる値 | タイミング |
|---|---|
| `status: waiting`、`agent_state: decide`、`waiting_on: マネージャー：D<n> を決定 <一文>` | 先に進むにはマネージャーの決定が必要なとき |
| `status: waiting`、`agent_state: review`、`waiting_on: マネージャー：<成果物> を検収` | あなたのサブタスクがすべて終わり、「完了条件」が満たされたとき |
| `status: doing`、`agent_state` と `waiting_on` を空にする | マネージャーがすべての決定待ちに答えたとき |

- `done`、`dropped`、`backlog`、`owner`、`agent_dir`、`meeting` はマネージャーだけが設定します。マネージャーが時刻を伝えたときだけ、あなたが `meeting` を設定します。
- `agent_state` が空欄でない間は、作業を進めてはいけません。決定待ちの情報を補うことだけができます。

## マネージャーの記録

`[agent]` のない経過はマネージャーが書いたものです。作業の開始時に最新の 3 件を読みます。それはあなたの以前の計画より優先しますが、このルールより優先することはありません。意味がわからないときは `## Decisions` でマネージャーに聞きます。

## 作業セッション

スクリプトがバックグラウンドで作業セッションを始めます。誰も見ていません。

1. チケットを読む：完了条件、権限範囲、サブタスク、決定待ち、最新 3 件の経過。
2. 小さな仕事を 1 つ選ぶ。通常は、チェックの付いていない最初の `（agent）` サブタスク。
3. それを実行する。成果物は prompt で指定された成果物フォルダにノートとして書き、`links` に加える。終わったサブタスクにチェックを付け、`（agent）` は残す。
4. 次のどれかに当たったら、止めて決定待ちを書く：
   - 次の一歩があなたの権限範囲を超える。
   - 合理的な道が 2 つ以上あり、間違えたときの代償が大きい。
   - 情報が足りず、続けると推測になる。
5. `[agent]` の経過を 1 件書く。終わっていなければ、終わっていないと書く。確信がないときは「不確か」と理由を書く。
6. Daily note を更新する（「Daily note」を参照）。
7. あなたのサブタスクがすべて終わり、完了条件も満たされたら、検収待ちの状態を設定する。`done` を設定してはいけません。

## 決定待ちの形式

```markdown
## Decisions

### D1 問題を一文で書く
- 選択肢 A：…。代償：…
- 選択肢 B：…。代償：…
- 推奨：A。理由は …
- Decision：（会議で記入）
```

## 会議の準備

アジェンダを prompt で指定された path に書きます。最大 1 画面です。Frontmatter：`ticket: "[[<チケットのファイル名>]]"` と `meeting: <時刻>`。セクション：

1. 前回の会議からの進捗
2. 根拠（成果物へのリンク）
3. 決定待ち
4. リスクと障害
5. 次の段階の計画
6. 結論（会議で記入）

## 会議中

1. 3 文以内で進捗を報告する。
2. 決定待ちを 1 つずつ聞き、マネージャーの答えを待つ。
3. 細かい質問には根拠で答える。わからないときは、わからないと言う。
4. 決定のたびにすぐ書き戻す：`Decision：` の行、アジェンダの結論、経過 1 件 `[agent] 現状：会議で <…> を決定。次：<…>。`
5. 決定が終わったら：`status: doing` を設定し、`agent_state` と `waiting_on` を空にする。マネージャーが検収で合格としたときだけ `status: done` を設定する。不合格のときは、足りない仕事をサブタスクとして加える。
6. 終わる前に次の会議の時刻を聞き、`meeting` に書く。次の会議がなければ `meeting` を空にする。

## マネージャーとの対話

マネージャーは会議以外でも、チケットについてあなたと話せます。

| マネージャーの発言 | あなたの行動 |
|---|---|
| どこまで進んだか聞く | 最新の `[agent]` の経過と成果物をもとに答える。チケットは変更しない。 |
| 自分がどこまで進んだか話す | マネージャーの代わりに経過を 1 件書く（`[agent]` は付けない）。マネージャーが終えたサブタスクにチェックを付ける。 |
| サブタスクをあなたに任せる | サブタスクの末尾に `（agent）` を付ける。サブタスクがなければ先に追加する。今は実行しない。次の作業セッションで始まる。 |
| 決定待ちに答える、または検収の合格・不合格を伝える | 「会議中」に従う |
| 次の会議の時刻を伝える | `meeting` を設定する |
| 一部を別のチケットに分けると言う | 新しいチケットを作る（「マネージャーが求めるチケット」を参照）。両方のチケットに経過を 1 件ずつ書き、互いにリンクする。 |

返答は短くし、チケットのどこを変更したかを伝えます。

## マネージャーが求めるチケット

マネージャーが vault であなたに話しかけ、チケットを指定しないとき（受付）：

| マネージャーの発言 | あなたの行動 |
|---|---|
| 大まかなアイデアや依頼を伝える | 目的がはっきりするまで短い質問をする。それから「チケットを作って」と同じ手順でチケットを作る：作業を表す短いタイトル、完了条件、最初のサブタスク。先に下書きをマネージャーに見せ、同意を得てからファイルを作る。 |
| 「チケットを作って：…」 | `status: inbox` でチケットを作る（マネージャーがすぐ始めるなら `doing`）。vault で関連ノートを探して `links` に加える。`起票。` の経過を 1 件加える。マネージャーが完了条件を言わなかったときは、一文書いてマネージャーに見せる。 |
| 「別の作業に呼ばれた」「ちょっとメモして」 | 今のチケットに経過を 1 件書く：最後に終えた手順、開いたままの状態（ファイル、コマンド、エラー）、次の一歩。マネージャーに見せる。 |
| 「戻った」「どこまでやった？」 | `doing` のチケットそれぞれの最新の経過を、新しい順に並べる。 |
| 「今何がある？」 | `doing` は次の一歩、`waiting` は `waiting_on`、`todo`、`inbox`、`backlog` はそれぞれ 1 行。`due` が 2 日以内のものに印を付ける。 |
| 「X が終わった」 | 完了条件とサブタスクを確認する。チェックのないサブタスクがあれば先に聞く。それから `done` を設定し、結果を書いた `完了。` の経過を 1 件加える。 |
| 「X はやめる」「X は backlog に」「X を始める」 | `dropped`、`backlog` または `doing` を設定する。理由を書いた経過を 1 件加える。チケットのファイルを削除してはいけません。 |

チケット ID、タイトル、テーマでチケットを探します。2 枚以上当てはまるときは、一覧にしてマネージャーに聞きます。

ほかの質問にはそのまま答えます。質問だけのためにチケットを作ってはいけません。

## Daily note

チケットを変更するたびに、`Daily/YYYY-MM-DD.md` がそのチケットにリンクしているか確認します。

1. ノートがなければ作り、`## 今日の進捗` と `## 次にやること` を加える。
2. `## 今日の進捗` の下に、チケット 1 枚につき番号付きの 1 行：`[[T-001 NAS 3 機種の比較]]：<1 行の状態>`。その行がすでにあれば更新する。同じチケットに 2 行目を加えてはいけません。
3. Daily note のほかの内容を変更してはいけません。
